# Testing Safety Nets — .NET Edition

No migration step executes without a safety net. This reference defines the testing strategies per phase — the goal is catching behavioral regressions BEFORE production, with tooling matched to the .NET target.

Verify tool versions via web search before writing them into a plan.

## Strategy Selection Matrix

| Situation | Primary | Supporting |
| --- | --- | --- |
| Legacy code with no tests | Characterization Tests | Golden Master |
| **Any legacy → .NET rewrite** | **Logical Parity Suite** | Contract + Characterization |
| API migration (→ ASP.NET Core) | Contract Tests | Parallel Run, Verify snapshots |
| Database migration (→ EF Core) | Data Consistency Validation | Parallel Run |
| Frontend migration (→ Blazor/MAUI) | Visual Regression + bUnit | E2E (Playwright), snapshot |
| Algorithm/business-rules rewrite | Property-Based Tests | Parity suite |
| Full system migration | Parallel Run | All of the above |

## Logical Parity Suite (flagship strategy)

**Purpose:** prove the new .NET implementation reproduces the legacy system's observable behavior — including its quirks — for a representative input space. This is the highest-value artifact in a rewrite: the same suite runs against BOTH implementations.

**Method:**

1. From the parity surface inventory (`research-phase.md` §1.5), pick every externally observable behavior: endpoints, screens' business actions, jobs, reports.
2. Write tests that feed representative inputs and assert the **actual legacy output** — generated by executing the legacy system (in-process harness, or HTTP against a running legacy instance).
3. Package the assertions so they run against an adapter: `ILegacySystem` (talks to legacy) and `INewSystem` (talks to the new ASP.NET Core API/Blazor backend). One test project, two fixtures.
4. Discrepancy → analyze: real regression, acceptable difference (new IDs/timestamps), or legacy bug that needs a product decision. Never silently replicate a bug — mark it `BUG — decide`.
5. When the discrepancy rate stabilizes below threshold, the domain is cutover-ready.

**Tooling (.NET):**

```markdown
### Testing: Logical Parity Suite

**Suite project**: `tests/Billing.Parity/`
**Harnesses**: `LegacyBillingFixture` (HTTP client → legacy app), `NewBillingFixture` (WebApplicationFactory → new API)
**Behaviors covered**: `POST /api/invoices` (happy, empty items, negative qty — legacy accepts, BUG flag), `MonthlyCloseJob`
**Discrepancy policy**: amounts exact, timestamps ±2s, IDs normalized
**Threshold**: < 0.1% mismatch over the recorded input set
**Known bugs captured** (decide, don't port): {bug} at `file:line`
```

## Characterization Tests

**Purpose:** capture what legacy code does today — bugs documented, not fixed — before any change. Use when coverage for the migrating module is <60%.

**Method (.NET):** xUnit test project pointed at the legacy module (or a thin executable wrapper for non-.NET code); mock externals with NSubstitute; assert ACTUAL outputs including edge cases: nulls, empty sets, boundaries, error paths.

```markdown
### Testing: Characterization
**Target**: `src/Billing/InvoiceService.cs` (`Create`, `Update`, `Cancel`)
**Coverage goal**: 80% before migration (dotCover/coverlet — `dotnet test --collect:"XPlat Code Coverage"`)
**Known bugs captured** (do not fix): {bug} at `file:line`
```

## Golden Master / Snapshot

**Purpose:** freeze complex outputs (reports, DTOs, rendered HTML) as reference files.

**.NET tooling:** `Verify` (`VerifyXunit`) — snapshot files auto-normalized for timestamps/Guids via scrubbers; `ApprovalTests` alternative. For HTTP responses, snapshot the serialized contract.

```markdown
### Testing: Golden Master
**Target**: `MonthlyReport.Generate()` → `migration-plan/golden-masters/`
**Normalize**: timestamps, GUIDs, machine names via Verify scrubbers
```

## Contract Tests

**Purpose:** prove the new ASP.NET Core API satisfies the same contract consumers already use — URL, method, request/response schema, status codes, error shapes.

**Method:** define the contract (existing OpenAPI/WSDL, or generated by observing legacy responses); run identical tests against legacy endpoint AND new endpoint — e.g., one xUnit `[Theory]` against both base addresses. Both must pass in CI before traffic moves.

```markdown
### Testing: Contract
**Contract**: Billing API — `POST /api/invoices` → 201 + InvoiceDto; `GET /api/invoices/{id}` → 200 | 404
**Validated against**: `legacy.base.url` AND `new-api` (WebApplicationFactory)
**Schema**: OpenAPI at `docs/api/billing.json`
```

## Parallel Run (Shadow Traffic)

**Purpose:** same inputs hit both implementations; legacy response serves production, new response is logged for comparison.

**.NET implementation:** YARP transform or middleware that mirrors requests to the new service and logs structured diffs; or application-level `Decorator` calling both `IBillingService` impls and comparing. New-side failures must NEVER affect the production response; normalize acceptable diffs (IDs, timestamps); log enough context to reproduce.

```markdown
### Testing: Parallel Run
**Target**: `CalculateShipping()` at `file:line`
**Compare**: amount ±0.01, date exact, carrier exact
**Threshold**: <0.1% mismatch over 10k calls, ≥2 weeks
**Telemetry**: `migration_path` tag + diff payload → {user's observability stack — ASK}
```

## Property-Based Testing

**Purpose:** falsify the port across the whole input space — invariants that must always hold.

**.NET tooling:** `FsCheck` (works from C# via `FsCheck.Xunit`), or `CsCheck`. Run against BOTH implementations for parity, or just the new one for invariants.

```markdown
### Testing: Property-Based
**Target**: `CalculateDiscount()`
**Properties**: result ∈ [0, originalPrice]; ≥ 50% max per rule at `file:line`
**Generators**: price [0.01..100000], qty [1..1000], tier [regular|premium]
```

## Data Consistency Validation

For EF Core dual-write phases: row-count compare (lag-tolerant), random sample field-by-field compare, checksums over key fields, scheduled reconciliation job. Record tables, frequency, tolerance, sample size, and alert threshold per domain plan.

**.NET implementation options:** a background `IHostedService`/`BackgroundService`, a Hangfire/ABP background job, or an external SQL script — pick what already exists in the environment.

## UI Testing (Blazor / MAUI targets)

- **bUnit** — component-level tests for migrated Razor components (render assertions, event handlers, JS-interop mocks).
- **Playwright** (`Microsoft.Playwright`) — E2E + **visual regression**: screenshot baselines of legacy pages BEFORE migration, pixel-diff after each migrated route (threshold <0.1%).
- **MAUI:** prefer unit-testing viewmodels (no UI runner needed) + manual/device verification checklist; Playwright does not cover MAUI native — record the residual risk.
- Keep a `migration-plan/visual-baselines/` folder of legacy captures.

## Testing Phase Timeline

| Migration phase | Required tests | Purpose |
| --- | --- | --- |
| Phase 0 (Safety Net) | Characterization, Golden Master, Parity suite skeleton | Capture current behavior |
| Phase 0 | Contract tests | Freeze the interface contract |
| Shadow | Parallel Run | Compare without risk |
| Canary | All above + metrics/alerts | Validate with real traffic |
| Ramp | Continuous contract + consistency | Detect drift at scale |
| Full | Full regression suite | Confirm no regressions |
| Post-migration | Remove parallel run, keep contract + parity suite as the permanent regression net | Ongoing protection |
