# Complete Reverse Analysis of the CAPTCHA System

## Scene
Objective: Reverse-engineer a large-scale captcha system in order to understand its complete working principle and verification process.

## Target Entity
- **nc.js** (72KB) — Core slider packed by Webpack (9 modules)
- **fireyejs.js** (583KB) — DSL VM interpreter (26 opcode custom instruction set)
- **awsc.js** (9KB) — module loader
- **secaptcha.js** (72KB) — WASM C compiled output (emscripten)
- **et_f.js** (262KB) — Another DSL VM type of file

## Verified Technical Solutions

### Plan A: Selenium + CDP Drag and Drop (Recommended)
Send native mouse events through CDP xKx0000xKx and complete verification in a real browser.
- Success rate: high
- Dependency: Chrome + xKx0001xKx

### Plan B: Playwright Headless Browser Runner
In Playwright, load the DSL VM and module loader, and expose the token via HTTP API.
- Success rate: Medium (depends on WASM initializing the environment)

### Plan C: Pure requests protocol verification
Directly call the API endpoint via an HTTP request for verification.
- Success rate: **Extremely low** (token is strongly bound to browser xKx0002xKx fingerprint)
- Not recommended

## Key Findings

1. **Tokens cannot be used outside of the browser** — Tokens generated by the DSL VM will be checked by the server for context consistency (TLS JA3, IP, Cookie, Referer, etc.) when submitted.

2. **fireyejs.js is not a WASM binary but a DSL VM** — a 583KB pure JS implementation of a custom virtual machine, executing encoded instructions through a loop of a 26-opcode interpreter

3. **nc.js 9 module has been 100% reverse-engineered** — including API endpoints, slider UI, interaction logic, ncSessionID algorithm, multilingual support, etc.

4. **The real WASM compilation output is secaptcha.js** — 72KB, using SharedArrayBuffer + Atomics, emscripten compiles C code

## Pitfall Record

1. A test appkey will not trigger real verification; you must use the appkey from the real page.
2. xKx0003xKx returning a specific status code indicates slider mode, while returning xKx0004xKx only confirms session creation
3. The URL events of JSONP requests in the performance log may be captured incompletely due to the injection method of the script tag
4. The exported function name does not exist in the DSL VM file (it is encoded by the VM), and the actual export is exposed through the module registry.

## Reusable Patterns

- **DSL VM Reverse Mode**: xKx0005xKx
- **General Architecture of the Verification Code System**: xKx0006xKx
- **CDP native event bypass**: xKx0007xKx bypasses detection, unrelated to WebDriver
