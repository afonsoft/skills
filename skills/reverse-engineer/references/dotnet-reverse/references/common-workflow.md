# .NET reverse engineering universal workflow

Full workflow details, IL patch reliability, string decryptor extraction, state machine identification, dnlib scripting.

## Complete workflow (end-to-end)

```text
1. Identify → Confirm that it is a .NET managed program (not native)
2. Detect → DIE / de4dot --detect identifies the obfuscator
3. Deobf → de4dot deobfuscation (retain the original sample)
4. Static → dnSpyEx browses the C# view positioning, and the IL view looks at the key logic
5. Dynamic → dnSpyEx debugger breaks in the key method and sees the runtime plain text
6. Patch → IL editor modification, Save Module
```

The products of each step must be placed on the disk: original sample `target.exe` → unpacked `target-clean.exe` → patched `target-patched.exe`.

## IL patch vs C# patch reliability

**Core conclusion: Use the IL editor for critical modifications, not the C# editor. **

| Dimensions | C# Editor (Edit Method C#) | IL Editor (Edit IL) |
|------|---------------------------|---------------------|
| Compilation failure risk | High (missing references, syntax, lambda rewrite failure) | Almost zero |
| Information fidelity | The compiler regenerates the IL, which may be different from the original IL | Replace it as it is and change it instruction by instruction |
| Applicable | Change a string, change a constant, simple logic | Change judgment, delete verification, change control flow |
| async/await/ state machine | Often compilation fails or is distorted | Directly change the state machine fields, reliable |

dnSpyEx's C# decompiler is based on read-only decompilation + attempt to recompile, and recompiling the code generated by the compiler (state machine, closure, `yield`) can easily fail. The IL editor is instruction-by-instruction editing, what you see is what you get.

### Typical IL patch mode

```text
Change the judgment (if (check) → always true):
Original: call bool Foo::Check()
      brfalse.s SKIP
Change: ldc.i4.1 ; push true
brfalse.s SKIP ; Now never jump, SKIP is not executed
Or more directly:
      ldc.i4.1
ret; method returns true directly

Change the judgment (if (check) → always false):
  ldc.i4.0
  ret

Delete the entire verification section:
All nop, or change to ret + correct return value

Change string constant:
It is usually OK to change the string in the C# editor (ldstr is directly changed to token), but if the string is in resources/encryption, the decryption logic must be changed.

Change numeric constants:
ldarg / ldc instructions directly change the operands
```

## State machine identification (async/await / yield)

C#'s `async/await` and `IEnumerator` yield are compiled into a **state machine**: the compiler generates a nested class, and the `state` field is used for switch dispatch in `MoveNext()`. The dnSpyEx C# view will be restored to async, but decompilation may cause distortion. The IL view is most accurate when looking at `MoveNext`.

```text
MoveNext structure of async/await:
  switch(this.<>1__state) {
case 0: ... logic before await; this.<>1__state = 1; await MoveNext;
case 1: ... logic after await;
  }

To patch async logic: change the state transfer in MoveNext or the judgment in a specific case.
Changing the C# editor to async will almost certainly fail → IL must be used.
```

## String decryptor extraction

See `obfuscators.md` for details. Here is the addition of dnlib scripted batch decoding of strings:

```csharp
// dnlib script: Scan all string decrypter calls, restore them at runtime, and write them back
// Usage: dotnet script decrypt.csproj target.exe 0x06000012
using System;
using System.Reflection;
using dnlib.DotNet;
using dnlib.DotNet.Writer;
using dnlib.DotNet.Emit;

var module = ModuleDefMD.Load(args[0]);
var decryptorToken = uint.Parse(args[1], System.Globalization.NumberStyles.HexNumber);

// Find the decryption method and invoke it using reflection (need to load the assembly into the AppDomain)
// Iterate through all methods and replace call Decryptor(token) with ldstr "decryption result"
foreach (var type in module.GetTypes())
    foreach (var method in type.Methods)
    {
        if (!method.HasBody) continue;
        var instrs = method.Body.Instructions;
        for (int i = 0; i < instrs.Count; i++)
        {
// Identify call to the decryptor pattern, invoke the decryptor to get plaintext, and replace with ldstr
// (The boilerplate for invoking the decryptor via reflection is omitted here, idea: load the original assembly →
//   MethodInfo.Invoke gets the plaintext → instrs[i] = OpCodes.Ldstr + operand=plaintext）
        }
    }

var opts = new ModuleWriterOptions(module);
module.Write("target-decrypted.exe", opts);
```

dnlib is the de facto standard for .NET metadata programming and is used internally by de4dot. Preferred when writing custom deobfuscation scripts.

## Key points of dynamic debugging

The dnSpyEx debugger is much more friendly to .NET programs than native:

- **Breakpoint is at the method entrance**: Right-click the method → Add Breakpoint
- **Look at the object value**: After stopping, the Locals / Watch window can directly look at the object fields and string contents.
- **Memory writing**: You can directly change the runtime variable value (Edit Value)
- **Exception Breakpoint**: Debug → Exceptions, check the exception type to be broken - the confusion is commonly used to drive the control flow with exceptions, and you can see the real path when breaking exceptions

### Exception driven control flow

Some obfuscators put normal logic into `try` and use `throw` + `catch` to make jumps. When viewed statically, IL looks like exception handling, but it is actually control flow:

```text
try { throw new CustomException(0x42); }
catch (CustomException e) {
    switch(e.Code) {
case 0x42: real logic A; break;
case 0x43: real logic B; break;
    }
}
```

Set an abnormal breakpoint (break `CustomException`) and track the value flow of `Code`, which is faster than hard-coding IL.

## Module initializer (Module .cctor)

The static constructor of the `.NET` module (`.cctor` of `<module>`) is executed first when the assembly is loaded. The obfuscator often places anti-tamper/decryption initialization here. Analysis order:

```text
1. First look at <module>.cctor (Module .cctor) - decryption/anti-debugging initialization
2. Look at Program.Main / Startup again
3. anti-tamper is in .cctor → patch .cctor first and then unpack it
```

## Extract configuration/C2/Key’s common pattern

Red team tools and loaders often embed configuration encryption in resources or fields and decrypt it at runtime:

```text
Positioning process:
1. Strings to see if there is plain text URL/IP (usually not after obfuscation)
2. Find the byte[] field + decryption method (AES/XOR)
3. Dynamically break at the return point of the decryption method and dump the decrypted plaintext
4. Common: AES-256-CBC with Key==IV (Codegate 2013 mode, see reverse-engineering/tools.md .NET section)
```

Refer to the specific configuration structure of the red team tool in `references/sharp-tools.md`.

## Boundary to reverse-engineering

- **IL2CPP / NativeAOT** → Compile to native, no CLR metadata → Use `reverse-engineering/` (IDA/r2), this skill only does recognition
- **Hosted .NET** (Standard C# exe/dll, Mono/Unity managed layer, Xamarin) → this skill
- **Mixed (native loader + .NET payload)** → The loader part is `reverse-engineering/`, dump the .NET payload and then cut the skill
